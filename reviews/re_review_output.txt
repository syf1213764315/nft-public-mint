## NEW / remaining findings

### NEW-1 â CRITICAL â PublicDrop ABI decode still wrong (finding #3 above)
Function `probe_public_drop_price` (line ~610). SeaDrop `PublicDrop` struct packs tightly. Reading words 0..4 as plain uint256 returns garbage for `startTime`, `endTime`, `max_per_wallet`, `fee_bps`. The "FREE vs PAID" verdict is correct only by luck when `startTime==0`; on any real drop the decoded fields are nonsense, and the comparison of `drop["mint_price_wei"]` to `0` only works because it's the low 80 bits of a packed word. **This is the same class of bug the script exists to prevent.** Either decode per the EIP-5669 packed tuple layout, or shell out to `eth_abi.decode`.

### NEW-2 â HIGH â RPC chain validation not actually pinning the pool
`validate_chain(primary, ...)` at line ~760 re-reads `eth_chainId` through `pool.call()` (which routes via ranked list, with possible failover). If a backup endpoint returns a different chain during failover, validation passes against the wrong chain. Pin to `fire.call("eth_chainId")` like the other fire-time reads. Also, between `pool.validate()` (line ~722) and the fire-time refresh there is no chain recheck against the *pinned* client â the pin is half-done.

### NEW-3 â HIGH â `tx_count` and balance fetched with `"pending"` but receipt uses `primary`, not `fire`
Receipt polling after broadcast (line ~810) goes through `primary.call(...)` which can be a *different* endpoint than `fire` once failover has happened (e.g. DRPC). DRPC supports `eth_getTransactionReceipt` so it usually works, but if the broadcast succeeded only on DRPC and NodeFlare then went down, you may poll a node that never saw the tx and time out. Also the signed tx was built from `fire`'s nonce â if `fire` was DRPC, that's fine; but the receipt path is mixed.

### NEW-4 â MEDIUM â `broadcast_same_raw` only broadcasts to 2 endpoints, but the second endpoint isn't DRPC-fallback aware
The pool ranks endpoints by latency+reliability; if NodeFlare is rank 1 and Alchemy is rank 2, both will try `eth_sendRawTransaction`. That's fine. But if NodeFlare fails with 429 *during* `broadcast_same_raw` (transport error after my "nonce too low" guard), the loop only iterates 2 endpoints and may give up before hitting a working one. The existing `call(..., max_retries=...)` default is `RATE_LIMIT_RETRIES=6` with 11s backoff = **66s block per endpoint** during broadcast of a real mint. Pass `max_retries=1` to `client.call` inside `broadcast_same_raw` (mirror the watch-loop fix). This is the same 66s-block bug fixed for the hot poll, just in a different call site.

### NEW-5 â MEDIUM â `--function-call` integer overflow / signedness
`parse_function_call` (line ~525) does `int(a, 0) & ((1 << 256) - 1)` â but for `uint128`/`int256` etc. this still works because the parser accepts any `uintN`. However, negative numbers via `int128` are not supported (parser would reject the `-`); for EVM ABI you need two's-complement. Not exploitable today because users only pass small quantities, but `safe_mint.py`'s own helper `abi_encode_call` uses `arg & ((1 << 256) - 1)` which *is* correct two's-complement â inconsistent with `parse_function_call`. If a user ever supplies a negative `int256`, the two paths disagree.

### NEW-6 â MEDIUM â `opensea-rest/scripts/osa_free_scan_rest.py` not in scope of this file but referenced in SKILL.md
SKILL.md claims "filter `price == 0`, PUBLIC-FREE vs NEEDS-ALLOWLIST" but I cannot verify that file in this review. Not a code defect here, just noting it was not provided for verification.

### NEW-7 â LOW â `gasPrice` EIP-1559 incompatibility on Base
`build_transaction` (line ~700) uses legacy `gasPrice` field. On Base (EIP-1559 enforced since 2024), legacy txs can still be mined but often at higher cost. With `eth_gasPrice` returning the base fee only, the 15% buffer is meaningless. Acceptable for Robinhood (still legacy-compatible), but the same script is documented for Base. Either gate `chain_id` to use legacy only on 4663, or switch to EIP-1559 envelope.

### NEW-8 â LOW â Keystore password strength check is per-command, not per-keystore
`create_keystore` (line ~545) requires 12+ chars, good. But `unlock_account` (line ~555) accepts *any* password that decrypts. If the user later migrates a weaker legacy keystore into this CLI (e.g. they generated it with the old repo), there's no strength recheck. Document, don't enforce.

### NEW-9 â LOW â `probe_supply` may report `sold_out=False` when total is None but max is finite
Line ~648: `sold_out = total is not None and mx is not None and total >= mx`. That's correct â but the inverse isn't printed. If `total is None` the user sees nothing about supply status and may mint a sold-out drop. Print a `[!] totalSupply unavailable` line for parity.

### NEW-10 â LOW â `redact` regex for private keys
Line ~110: `(0x[a-fA-F0-9]{4})[a-fA-F0-9]{40,}` redacts 40+ hex chars â but tx hashes are exactly 64 hex chars after `0x`. False positives are acceptable, but the regex will *also* redact EIP-55 checksum addresses if they appear unquoted in errors. Already done, just confirm it doesn't accidentally break log readability.
